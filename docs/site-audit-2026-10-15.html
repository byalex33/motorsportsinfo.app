[Medium] Anyone can flood push subscriptions and make the alerts cron drop real Session Reminders

SEC-1

// how it was found

POST /api/push/subscription (src/app/api/push/subscription/route.ts:41) has no rate limit, no per-client cap and no total row cap. The endpoint check (src/server/alerts/validation.ts:55) only requires a push-service host, so https://fcm.googleapis.com/fcm/send/<anything> with any base64url keys is accepted and upserted as a new row.

Each minute runAlerts loads every subscription once something is due (src/server/alerts/run.ts:38) and sends to every matching one, 10 at a time with a 10 s timeout each (src/server/alerts/push.ts:7, :45), inside a 60 s function (src/app/api/cron/alerts/route.ts:7). Reminders are claimed before they are sent (run.ts:126). If a run times out, every claimed but unsent reminder is never retried.

Effect: a script that registers a few thousand fake FCM endpoints following every Series makes the next busy minute (a Race start) outrun the 60 s limit, and real followers miss their reminder. Bogus rows are pruned only after a send fails, so the script can simply re-register. No data is exposed.

Needs checking: whether the Vercel Firewall rate-limit rule the 11 Oct audit recommended (SEC-1 there) exists. Nothing in the repo or vercel.ts defines it.

// how to fix

  • Add a Vercel Firewall rate-limit rule on /api/push/subscription (for example 10 requests per minute per IP, then 429).
  • Give the cron a time budget: stop claiming new reminders when about 45 s have passed, so anything unclaimed waits for the next minute instead of being lost.
  • Optionally cap the table (refuse new endpoints above, say, 50,000 rows) and log when the cap is hit.
